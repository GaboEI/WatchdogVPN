# Network Context: Product Boundary and Threat Model

WatchdogVPN can understand the local network environment so it can explain state
and, when explicitly enabled, offer optional automation.

That capability is useful but sensitive. A network name, access point
identifier, interface name or route shape can reveal where the user is, who
operates their network, which organization they belong to, or how their machine
is connected. WatchdogVPN must treat network context as local private context,
not as anonymous telemetry.

## Product Boundary

Network context is local private context. The product may read it to explain
state and to drive optional, explicitly enabled automation, but it must not treat
those facts as anonymous telemetry or as a policy authority.

## Trust Boundaries

| Boundary | Trust decision |
| --- | --- |
| Local host to WatchdogVPN daemon | Trusted only through existing daemon/systemd permissions and validated config. |
| NetworkManager or system route events to WatchdogVPN | Platform input, but not a policy authority. Events may be stale, missing, partial or unavailable. |
| Wi-Fi SSID/BSSID to WatchdogVPN | Sensitive local context. It may identify home, work, travel or organizational location. |
| Interface names to WatchdogVPN | Potentially sensitive local context. Names can expose hardware, virtualization topology, tethering or operator conventions. |
| Captive portal / offline detection to WatchdogVPN | Advisory signal only. It must not silently override user intent or protection state. |
| Diagnostics engine to CLI/TUI/support export | Structured facts must be classified before display/export; normal outputs must be redacted by default. |
| LAN proxy/gateway state to diagnostics | Read-only status only. Diagnostics must not weaken the LAN sharing bind/auth/firewall/DNS contracts. |

## Data Classification

### Persistable By Default

These fields may be stored by default because they are product configuration,
low-sensitivity policy state, or intentionally coarse operator choices:

- automation enabled/disabled state;
- trusted/untrusted policy names chosen by the user;
- user-authored network profile labels that do not embed raw SSID/BSSID by
  default;
- explicit policy actions such as connect, disconnect, keep current state,
  warn only or manual mode;
- coarse policy timestamps such as last policy edit time;
- redaction preferences and diagnostics-export preferences;
- stable opaque IDs generated by WatchdogVPN for user-created network profiles.

Constraints:

- user labels are still local configuration and must be redacted from normal
  support export unless the user explicitly includes them;
- stored policy must never imply that an automatic action is enabled unless the
  user explicitly opted in or confirmed it;
- no persisted field may contain raw passwords, provider tokens, private keys,
  LAN proxy credentials or subscription URLs.

### Persistable Only With Explicit Consent

These fields may be persisted only with explicit, reviewable consent and clear
CLI wording:

- raw Wi-Fi SSID;
- raw Wi-Fi BSSID;
- raw wired network identifiers when a platform exposes them;
- raw interface names used as network-profile match keys;
- default gateway MAC or other link-layer identifiers;
- recent network transition history;
- captive-portal detection history;
- public exit IP history;
- per-network automation outcome history.

Required controls before persistence:

- default-off;
- explicit command or confirmation before storing;
- display that the value may identify a location or organization;
- bounded retention or an explicit delete path;
- emergency purge path;
- excluded or redacted from normal support export;
- import/backup handling that keeps the value private unless the user
  explicitly exports it.

### Transient Only

These fields may be read transiently for immediate diagnostics or policy
evaluation, but must not be written to persistent stores or normal reports by
default:

- currently connected SSID/BSSID;
- current interface names and interface types;
- current default route and gateway details;
- current DNS server addresses;
- current captive-portal/offline probe result;
- current public exit IP test result;
- current TUN, local proxy, system proxy and LAN gateway state;
- current route-table summary;
- current provider update status if derived from live runtime checks.

Transient output rules:

- human output may show these facts only in an explicit diagnostic command or
  status view where the user requested local context;
- JSON output must mark whether a value is raw, redacted, hashed, unavailable
  or unsupported;
- support export must redact or hash these values by default;
- diagnostics must distinguish observed live state from configured intent.

### Forbidden

The following must not be stored by network context or normal diagnostics:

- private keys;
- passwords;
- provider tokens;
- subscription URLs with credentials;
- raw provider import payloads;
- LAN proxy credentials;
- raw packet payloads;
- browser URLs;
- DNS query history;
- raw destination history;
- per-flow timestamps;
- process executable paths in network-context history;
- unredacted support bundles;
- external geolocation history derived from SSID/BSSID/public IP.

## Automation Safety Contract

Network-aware automation must never silently become a second rotation/recovery
engine or a hidden route/DNS mutator.

Minimum contract:

- automatic network-context behavior is disabled by default or explicitly
  confirmed during setup;
- every automatic action must be explainable before and after it runs;
- every automatic action must be disableable;
- every automatic action must be reversible or fail without mutating state;
- unsupported environments must degrade to manual mode with an honest
  diagnostic;
- stale/missing network events must not trigger destructive or
  privacy-sensitive actions;
- captive-portal and offline signals are advisory until validated against the
  current route/DNS/capture state;
- automation must not enable LAN sharing, gateway mode, system proxy,
  forwarding, DNS mutation or route mutation unless that behavior is explicitly
  implemented and validated.

Rejected automation behaviors:

- storing raw SSID/BSSID by default;
- creating a Wi-Fi location history;
- silently auto-connecting on any newly observed network;
- silently disconnecting on any newly observed network;
- treating captive portal detection as proof that protected traffic is safe;
- reporting unsupported network-monitor environments as healthy;
- exporting raw network identifiers in normal support bundles.

## Diagnostics Safety Contract

Unified diagnostics must be structured first and display/export second.

Required properties:

- distinguish configured intent, observed live state and unsupported checks;
- include confidence or status for route/DNS/capture predictions;
- report unavailable data as `unknown` or `unsupported`, not healthy;
- identify when a fact is redacted;
- keep normal support export redacted and user-reviewed by default;
- never include raw secrets, raw metric stores, raw DNS/destination histories
  or LAN credentials;
- preserve route diagnostic honesty: configured-policy diagnostics are not
  runtime packet proof;
- preserve LAN diagnostic honesty: manual gateway DNS mode must not be reported
  as automatic LAN DNS protection.
